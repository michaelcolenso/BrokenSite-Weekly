## Executive Summary

BrokenSite-Weekly has **good engineering and a real market**, but it currently has **two different products living in one repo**, an **empty pilot dataset**, and — most importantly — **no customer acquisition channel**. The code is ~80% of the way to a sellable v1; the business is ~20% of the way.

The single highest-leverage move is not more code. It is resolving the strategic fork, running the Seattle scan, and putting a free sample list in front of 50 web freelancers. Everything else is secondary.

**Top 5 findings, ranked by impact on success probability:**

1. **Strategic fork is unresolved.** README/.env describe a Gumroad + Google-Maps-scraping + automated-outreach product. HANDOFF.md describes a Stripe/Resend, no-outreach, honest-crawler, Seattle-only product. Both are partially built. Agents and future-you will keep building the wrong half.
2. **The pilot could not run.** `data/metros/seattle.csv` contains only a header row, and there was no scanner orchestrator. The orchestrator (`scanner/__main__.py`) is now built on the `v1-rebuild` branch; the empty CSV remains the blocker.
3. **Your lead source is your biggest legal/operational risk.** Google Maps scraping (legacy) violates Google's ToS and directly contradicts HANDOFF hard rule #2. The v1 data-source question (HANDOFF open question #4) is still unanswered.
4. **Distribution is unbuilt.** "$1K MRR via Gumroad" assumes subscribers appear. There is no landing page, no free sample, no channel plan. This — not detection quality — is what kills lead-gen products.
5. **The project has stalled for 7+ weeks.** The repo carries forward motion debt: stale open questions, dead modules, and divergent docs. A cleanup + recommitment pass is worth more than any new feature.

## 1. The Two-Product Problem (Critical)

### What's in the repo today

| Dimension | Legacy (`src/`, README) | v1 rebuild (`scanner/`, HANDOFF.md) |
|---|---|---|
| Lead source | Google Maps via Playwright (+ Yelp) | Metro CSV → honest crawler |
| Payments | Gumroad API | Stripe Payment Link (planned) |
| Delivery | SMTP w/ CSV attachment | Resend + signed report links (planned) |
| Outreach | `outreach.py`, `contact_finder.py`, `warm_delivery.py` — built | Hard rule #1: **never build** |
| Crawler ethics | Anti-bot-adjacent (Playwright on Google) | Honest UA, robots.txt, 10s/domain |
| Scope | 10 cities × 10 categories | Seattle only, 5-subscriber gate |
| Price | $50/mo | $39/mo |

### Assessment

The v1 HANDOFF is the **better strategic document** — tighter scope, explicit validation gate, sane compliance posture. But the README (the repo's front door, and what any agent reads first) still describes the legacy product. Meanwhile `outreach.py`, `contact_finder.py`, `warm_delivery.py`, and `yelp_scraper.py` exist in the tree as direct contradictions of hard rule #1.

The legacy codebase is not worthless: ~16K lines with a genuinely strong test suite (`test_db.py` 724 lines, `test_scoring.py` 1,343 lines, CI on every push). The delivery engine — `db.py` (dedupe, tiers, exports), `delivery.py`, `subscriber_prefs.py`, `weekly_summary.py` — is tested infrastructure you should **keep**.

### Recommendation

- **Declare v1 the product.** Update README to match HANDOFF (or merge them). One product, one story.
- **Amputate, don't delete:** move `outreach.py`, `contact_finder.py`, `warm_delivery.py`, `yelp_scraper.py`, `competitor_analysis.py` to a `legacy/` directory or an `archive/legacy` branch. Keep git history, remove them from the build surface. This kills the temptation and the confusion in one move.
- **Keep and reuse:** `src/db.py` schema, tier gating (`GUMROAD_PRO_SEAT_CAP` → metro-exclusive seats), `delivery.py` (swap transport to Resend), `weekly_summary.py` (operator KPI email), the entire test harness.
- **Payments: reconsider Gumroad for the pilot.** HANDOFF chose Stripe Payment Links, but Gumroad removes subscriber-management code entirely (it already handles billing, churn, taxes, and gives you the buyer list via API — which `src/gumroad.py` already reads). For a 5-subscriber validation gate, zero portal code beats $30/mo in fee savings. Decide once, write it in HANDOFF, close open question #2.

## 2. The Pilot Cannot Execute (Critical, Fixable This Week)

Two hard blockers to your own Phase 1 gate:

**a) `data/metros/seattle.csv` is empty (header only).** The scanner has nothing to scan.

**b) There was no scanner orchestrator** — `scanner/` had `crawl.py`, `checks/p0.py`, `score.py`, `emit.py`, `screenshot.py` but nothing wiring them together. **Resolved on the `v1-rebuild` branch:** `scanner/__main__.py` now runs the full pipeline end-to-end (`python -m scanner --metro seattle`): metro CSV → polite crawl → 8 P0 checks → severity/tier → Tier A/B screenshots → `results.json` + `verification_sample.csv`. Auxiliary check requests (form actions, image HEADs) go through a new `DomainThrottledSession` so they obey the same 10s/domain pacing and honest UA as the crawler. Covered by 15 offline tests in `tests/test_scanner_orchestrator.py`.

The remaining blocker is **(a)** — populating `seattle.csv`.

**Throughput check (the politeness math works):** at 10s/domain with 4 concurrent domains → ~1,440 domains/hour. Seattle-relevant businesses in target verticals: ~3–6K. A full weekly scan fits in 2–4 hours — comfortably inside a systemd timer window. The v1 rate limits are not a scaling problem at pilot scope.

## 3. Lead Sourcing: The Real P0 Decision (High)

HANDOFF open question #4 ("Places API budget or WA SoS-only?") is the most consequential unanswered question in the repo.

| Source | Cost | Compliance | Website URLs? | Verdict |
|---|---|---|---|---|
| Google Maps scraping (legacy) | Free | **ToS violation; contradicts rule #2** | Yes | Retire |
| Google Places API (official) | Paid, metered | Fully compliant | Yes (`websiteUri` on higher-tier SKUs — verify current pricing/field masks) | **Recommended for pilot** |
| OpenStreetMap / Overpass | Free | Compliant (ODbL — mind attribution/share-alike) | Spotty, but Seattle is well-mapped | Good free supplement |
| WA Secretary of State | Free | Compliant | **No URLs** — business registry only | Not viable as primary; useful for cross-checking legitimacy |
| Outscraper/Apify | Cheap (~$5–20/metro) | Gray-zone, but risk is outsourced | Yes | Acceptable fallback if Places costs surprise |

**Recommendation:** budget $25–50 for the Seattle pilot on the official Places API, with ODbL-attributed OSM as a supplement for coverage gaps. Cache every place result (place IDs are stable; re-fetching is pure waste). The HANDOFF's instinct toward compliance is correct — a lead-gen business whose data pipeline can be ToS-killed overnight has no enterprise value; one built on licensed/official sources does.

Also flag: `stale_copyright ≤ 2021` is a decaying signal — every year the pool of qualifying sites shrinks and the check's meaning drifts. Make the threshold year a config value (`STALE_COPYRIGHT_CUTOFF`), not a regex constant.

## 4. Distribution: Where This Product Actually Lives or Dies (Highest Strategic Risk)

Your own dry-run data tells the story: **18 leads from ~580 businesses (~3% hit rate)**. That means a Seattle scan yields maybe 100–200 leads. At $39/mo with a 5-subscriber gate, the entire pilot revenue is $195/mo. The detection engine is demonstrably good enough. **The binding constraint is finding 5 freelancers who pay.**

What the repo currently has for distribution: nothing. What it needs, in order:

1. **Free weekly sample (your planned `trades-cut.csv` — build it first, not last).** 10 real Seattle leads with screenshot evidence, no email gate for the first month. This is your entire marketing asset.
2. **A landing page that sells the evidence, not the concept.** "We scanned 4,212 Seattle business websites. Here are 17 with expired SSL certificates — with screenshots." A screenshot of a plumber's broken site converts better than any copy about "lead generation." The `screenshot.py` infrastructure already exists; make screenshots the hero of the page.
3. **Manual founder outreach is legal and encouraged** — HANDOFF bans *automated* outreach, not *you* emailing 30 freelancers in r/webdev, Indie Hackers, local WordPress meetups, and r/smallbusiness "for hire" threads. Twenty personalized emails with the free sample attached will teach you more than any feature.
4. **pSEO play (your home turf):** per-metro pages — "Seattle web design leads," "Tacoma broken websites" — each embedding 3–5 real (anonymized-enough) examples with screenshots. This is a defensible organic channel that compounds, and it costs you nothing but templates.
5. **Pricing structure to reduce churn:** keep $39/mo base; add a **metro-exclusive tier at $99/mo capped at 3 seats** (the `GUMROAD_PRO_SEAT_CAP` concept already exists in legacy config — port it). Exclusivity is what agencies actually pay for, and caps create urgency without automation.

**Add a demand smoke-test before Phase 2 infrastructure:** landing page + free sample + 20 manual emails. Target: ≥3 "I'd pay for this" replies or ≥1 pre-order before building the Worker/D1 delivery pipeline. This matches how you've gated other data products — and this one deserves the same discipline.

## 5. Technical Audit — What's Strong, What's Debt

### Strong (keep, don't touch)

- `scanner/crawl.py` — genuinely well-built: robots.txt caching, per-domain 10s pacing, global concurrency cap, honest UA, blocked-state recording. This is the compliance core and it's right.
- P0 check implementations in `checks/p0.py` — clean, regex-driven, each returning structured `{check_id, triggered, evidence, severity}`. The evidence strings are an underrated product asset (see §4.2).
- Test suite breadth and CI on every push/PR.
- `.gitignore` properly excludes secrets/artifacts; systemd unit + timer + backup script exist.
- The validation-gate discipline in HANDOFF (90% true-positive requirement with a verification sample) is exactly right.

### Debt & gaps (ranked)

1. ~~No scanner orchestrator~~ — **done on `v1-rebuild`** (see §2).
2. **Verification UX:** the 90% TP gate requires you to eyeball samples. Wire screenshots into `verification_sample.csv` rows (path or base64 thumbnail) so manual review takes 10 minutes, not an hour.
3. **`.claude/agents/warm-lead-architect.md` and `docs/superpowers/` plans reference the legacy outreach surfaces.** Prune agent configs that contradict hard rule #1 — an agent given a warm-lead-architect prompt *will* build warm-lead features.
4. **ROADMAP.md (January 2026) and DEEP_REVIEW.md are stale relative to HANDOFF.** They optimize the legacy pipeline (parallel scoring, query rotation across 10 cities) that v1 abandons. Either annotate them "LEGACY — superseded by HANDOFF.md" or delete. Stale plans are how agents drift.
5. **Scoring additions worth doing (cheap, high-signal), in priority order:**
   - Response time >5s → +20 (data already collected)
   - Redirect chains ≥3 → +15 (`len(response.history)`, free)
   - `Last-Modified` >2 years old → +20 (free header parse)
   - Skip: meta description/H1 checks — SEO trivia, not breakage; they dilute the "objective technical breakage" positioning that makes your lists credible.
6. **Freshness/rescore policy:** store `last_scanned_at` per domain; rescore leads older than 90 days; auto-drop leads whose checks no longer trigger (with a note in the DB — "fixed sites" are churn data for your weekly summary, not wasted work).
7. **Ops hardening (small):** healthchecks.io-style dead-man's ping at end of each weekly run; the existing `weekly_summary.py` KPI email to yourself is sufficient observability at this scale — resist building dashboards.

### Correctness notes on legacy modules being kept

- `delivery.py` CSV writing: verify the CSV-injection sanitization flagged in ROADMAP was actually applied before reusing for subscriber delivery (formula-prefix escaping on all user-originated fields).
- `db.py` dedupe: confirm the atomic `INSERT ... ON CONFLICT` path from `implementation.md` Phase 1 landed; if `is_duplicate()` check-then-insert remains, fix it before parallel scanning is ever enabled.

## 6. Compliance Posture (Good — Keep It That Way)

The HANDOFF hard rules are the strongest part of this project's design. Reinforce three points:

- **Publish `/bot` early** (open question #1 implies the domain isn't even confirmed). A real bot-info page with an opt-out email is cheap legal armor and a trust signal. Pick the opt-out email now (open question #5) — `optout@` is fine.
- **Data minimization is already correct** (business-public fields only, no personal emails). Keep it; it's what separates you from the scrape-and-spam crowd and what you'd say in a jurisdiction inquiry.
- **Subscriber delivery email is transactional** — minimal CAN-SPAM exposure, but keep an unsubscribe link anyway (Gumroad handles most of this if you stay on it).
